# Research — Mastra's multi-user, multi-channel agents → Atrium

## Provenance
- Date: 2026-08-12. Target project: **Atrium** (this repo). Question: *what do Mastra's multi-user/multi-channel agent patterns transfer to Atrium's control plane and its deferred `ConversationSource`/`ExecutionProvider` seams* — analog/how-to, practice-led.

## What Mastra is
A TypeScript agent framework. The post is a first-party feature-launch/engineering-diary for its **channels** feature — putting one agent into Slack/Discord/Telegram/Teams/WhatsApp/iMessage/GitHub. Thesis, in their words: *"Single-user agents in 1:1 web chat are the easy version… Multi-user agents is life on hard mode."* The framework's pitch is that it absorbs the hard-mode complexity (OAuth, HMAC verification, encrypted creds, per-platform event normalisation, concurrency, per-thread isolation) so the app author writes the same `new Agent({…})` regardless of channel.

## THE load-bearing finding (the inversion)
**Mastra's entire multi-user model is identity-by-CONVENTION, not enforcement.** The caller passes `resourceId`/`threadId`; the library trusts them. Its own security note: *"Set the speaker from your authenticated request context, never from the request body. If a client can choose its own author_id, one user can impersonate another."* There is no ACL between resources; isolation is "everyone points at the same id."

Atrium is the **enforced** version of the same model — server-side identity (#96), the certify boundary (#102), attention/authorship that can't be spoofed. So: **Mastra = right primitives, wrong (unenforced) foundation; Atrium = enforced foundation, no adapter breadth.** The whole transfer is to lift Mastra's catalog onto Atrium's covenant spine, and to *refuse* its two consent-by-trust shortcuts (below).

## Comparator — concept vs transferable pattern

|---|---|---|---|

Atrium lacks the durable per-participant "working memory" + semantic recall. Borrow those two, under the covenant. |
| **Channel adapters** | `channels:{adapters:{slack:createSlackAdapter()}}` on the agent; auto-registers `/api/agents/<id>/channels/<platform>/webhook`; built on **Vercel Chat SDK** unified inbound (`onDirectMessage/onNewMention/onAction/onReaction`); Mastra owns OAuth, HMAC (5-min replay window), encrypted creds (AES+HKDF), token rotation, multi-tenant lifecycle; platform userID→resourceId, threadID→threadId | **YES — this is the reference design for `ConversationSource`** | init.md deferred this seam; Mastra has worked it out. The uniform inbound event shape + "adapter owns the boring plumbing" is exactly the shape. Map platform-user→Atrium participant, platform-thread→room, with ENFORCED identity (not trust-the-payload). |
| **Signal API (concurrency + async events)** | Many users post into one thread mid-stream; naive per-message `stream()` races. `agent.sendSignal` interrupts a live run ("stop"/"also do X"), modes `queue`(default)/`debounce`/`batch`/`skip`. **Non-obvious insight where Atrium is AHEAD:** Mastra keeps **channels** (inbound chat) and **signals** (external events) as two separate mechanisms it never unified. Atrium already has ONE typed, per-room-sequenced event spine (#12) — so it is positioned to unify "a Slack message," "a CI result," and "a webhook" as one typed event into the room, which Mastra can't cleanly do. Don't copy the two-mechanism split; collapse it.

## Strategist — ranked patterns (against Atrium's bottleneck)

**Atrium's bottleneck/frontier (from the map + RETRO + memory):** the trustworthy world is *built* (destination #89 reached); the OPEN frontier is Phase 3 — the control plane and its two deferred adapters (`ConversationSource`, `ExecutionProvider`) and the Glance agent→plan→session model (#111/#112). Atrium has an enforced world with **no adapter layer**. Mastra is *entirely* an adapter layer. So concepts are ranked by how much they flesh out those two seams.

**1 — Channel-adapter architecture → build `ConversationSource` on this reference.**
- Pattern: a per-platform adapter that normalises inbound to ONE typed event shape and owns all the boring plumbing (OAuth, signature verification, encrypted creds, token rotation, multi-tenant lifecycle); the core agent/room is channel-agnostic; platform-user→participant, platform-thread→room.
- Value for Atrium: this is the seam init.md left as a stub, worked out. It directly attacks the frontier (no channels today). Put it on ENFORCED identity — the adapter resolves a platform user to an *authenticated Atrium participant*, never trusts a payload id.
- Where: a new `packages/ingest`-adjacent adapter layer feeding `apps/server`'s room-events; the participant-resolution goes through `packages/auth`/#96.
- **Build vs buy:** BORROW the architecture; **BUY** Vercel's Chat SDK adapters for per-platform inbound parsing (the hard, boring, undifferentiated part) — reinventing Slack/Discord event parsing adds nothing. Build the Atrium-side mapping + enforcement.

**2 — The Signal/interrupt primitive + per-session workspace resolver → the `ExecutionProvider` + the Glance channel loop.**
- Pattern (a): an interrupt primitive — a running agent turn can be interrupted/steered by a new inbound signal (queue/debounce/batch/skip); and a session/thread can *subscribe* to an external resource so a later event (CI, PR, webhook) resumes it. Pattern (b): a per-session sandbox resolver keyed on the session/plan id → an isolated workspace via a pluggable sandbox provider.
- Value for Atrium: (a) is exactly Glance's channel-loop concurrency and the #112 execution/cost stream — Atrium has ordered events but no interrupt/resume-on-external-event. (b) is exactly Glance's *session = process (own address space)* and the campaign's worktree-per-session, generalised — the reference isolation model for the execution adapter.
- Where: the `ExecutionProvider` seam; the agent's channel loop (#111's daemon); #112's cost/execution stream.
- **Build vs buy:** BORROW both patterns; consider **BUY**ing a sandbox provider (E2B/Daytona/ComputeSDK) for the execution adapter's isolation rather than hand-rolling sandboxes.

**3 — Cross-channel gate rendering, MINUS the LLM-judge fallback → the covenant, channel-aware.**
- Pattern: render the human-approval/certify gate per channel capability (buttons where available, graceful fallback where not) from ONE gate definition, no app-code branching. **Explicitly reject** the "LLM classifies the user's yes/no" fallback.
- Value for Atrium: when `ConversationSource` spans channels, the certify/`human=init` gate (#102, #110, Glance's hold-to-arm) must render everywhere — but Atrium's whole thesis is that a human's *explicit act* certifies, never a model's guess. This is where borrowing Mastra's rendering while refusing its fallback *is* the differentiation. On a channel that can't render an explicit act, the correct Atrium behaviour is to **withhold** the gate (it stays owed) — not to let an LLM infer consent.
- **Build vs buy:** BORROW the per-channel rendering; the refusal of the LLM-judge fallback is a covenant invariant to write down.

**4 — Harness-engineering-over-context-engineering + attribution.**
- Pattern: give a session tools to fetch context on demand, scope it to the current room by default, prefix by author; don't front-load. Value: the right shape for how `ExecutionProvider` feeds a session — matches Glance session=own-context. BORROW the practice.

**5 — Resource-scoped working memory + semantic recall (weigh against a covenant tension).**
- Pattern: a durable per-participant profile (working memory) + vector recall over history, scoped by the participant, shared across their rooms.
- Value: a genuine capability gap (Atrium has the append-only ledger + current-state, but no durable per-participant "what I know about this person" or semantic recall). BUT a covenant tension: **a machine's memory of a person is a `~` claim, not a fact** — so working memory must live *under* the covenant (drafted, human-visible, correctable), not as trusted hidden state. Lower rank: it's speculative and needs a decision (does Atrium want per-participant machine memory at all, and how does it stay honest?). Flag as a possible Phase-3 decision, not a build yet.

## Bottom line
Mastra is the best available reference for the two seams Atrium deferred — `ConversationSource` (rank 1) and `ExecutionProvider` (rank 2) — and it validates the Glance execution model (session=process, per-session sandbox, resolver-scoped). Adopt its *architecture* and buy its two hardest boring pieces (Chat SDK adapters; a sandbox provider). Refuse its two identity shortcuts — trust-the-caller resourceId and LLM-judges-consent — which are exactly the covenant's reason to exist. And where Mastra split channels from signals, Atrium's one typed event spine can unify them.
