## 2. Accomplishments — what it genuinely got right

**NIP-RS (Cross-Device Read State Sync), `docs/nips/NIP-RS.md`, 797 lines.** This is the standout artifact in the repo. It's a from-scratch CRDT protocol for synchronizing per-device "read" position across clients over encrypted Nostr events, plus a bolted-on "manual mark-as-unread" override layer built as set/clear/baseline counters merged by componentwise `max()`. Notable engineering choices, all normatively specified:
- Grow-only max-register CvRDT for read frontiers; a second three-key counter CRDT (`ov_s`/`ov_c`/`ov_b`) for manual overrides, with a proven "clear-wins" tie policy and a "tombstone floor" compaction rule that prevents a stale device snapshot from resurrecting a cleared override.
- A "Full-State Load" completeness procedure (~lines 321–379) that solves a genuinely hard problem: proving, against relays that silently cap query results, that a client has seen *all* of its own read-state coordinates, using a descending-cursor enumeration fenced by a live subscription established before the first query. It states five explicit conformance requirements a relay must meet (newest-first prefix delivery, non-decreasing cap, a floor of L=2, push delivery, and an ordering "delivery barrier") and proves the floor value is exactly 2 by argument.
- Backed by a real formal-verification artifact: `docs/formal/nip-rs-unread/{model.py,exhaustive.py,mutation.py,NOTE.md}` — bounded exhaustive model checking with a 9-mutant harness that the spec cites by name (NIP-RS.md line 561, 605–611: *"See `docs/formal/nip-rs-unread/` for the exhaustive proof and mutation harness"*). A sibling formal directory `docs/formal/nip-pl/` covers a separate protocol layer.
- Traced through PR #2864, "docs(nips): add single-coordinate manual-unread override layer and verification model to NIP-RS" — landed as part of the v0.5.3 changeset.
This is a case of a chat client treating "what have I read" as a distributed-systems correctness problem worth formal proof, not a UI checkbox — directly relevant to any product making claims about reliable unread/catch-up state.

**buzz-agent / buzz-dev-mcp** (`VISION_AGENT.md`): a from-scratch, minimal ACP agent (speaks Agent Client Protocol over stdio) and a separate MCP tool server (shell + file editor), deliberately kept small and decoupled — "two crates... no coupling between them," "auditable in an afternoon." Concrete hardening claims: zero `unsafe`, zero panics, process-group kill on every exit path, bounded output/history, up to 8 concurrent sessions per process. This is agent *tooling* craft (the runtime), separate from agent *permissioning* (below).

**Agent identity/permissioning model.** Per README ("Let an agent triage a bug without giving it the keys to the kingdom... Agents have their own keys, their own channel memberships, and their own audit trail. Scoped by identity, not by permission flags") and `CONTRIBUTING.md`'s event-kind model, every actor — human or agent — is a Nostr keypair, and access is channel membership, the same primitive for both. Agents surface in the UI via a `kind:10100` "agent profile" event that badges them as "agent" in member lists and @mention autocomplete (per issue #3996, filed by gdotbat, 2026-07-31). PR #4063 (`buzz doctor`, unmerged as of the clone but reviewed same-day) adds a non-mutating preflight CLI command with 8 unit tests, structured exit codes (0/2/3 matching auth-vs-transport failure classes), and explicit "never exposes private key material" guarantees — a small but real piece of operational maturity for agent-facing tooling.

**Test/CI culture as a subsystem in its own right** (see §6) — `just ci` gate, path-filtered CI jobs, DCO enforcement, a file-size ratchet script, and release-contract tests that test the release *process* itself (`scripts/test-release-ref-contract.sh`, `scripts/test-desktop-release-candidate.sh` run inside CI's own `changes` job, per `.github/workflows/ci.yml`).

## 3. Onboarding and defaults

From README.md ("Getting started" + "Quick start" + config sections, lines 113–259) and CONTRIBUTING.md:

- **Four onboarding paths, explicitly branched by user type:** (1) "I just want to try the app" — download a packaged build (macOS `.dmg`, Linux `.AppImage`/`.deb`, Windows `.exe`); (2) "I want my own hosted relay" — one-click Railway deploy (added by community PR #2733, 2026-08-01, flagged "community-maintained, not an official Block build"); (3) "I work at Block" — internal pre-wired build, zero config; (4) "build & run from source" — the dev path.
- **Zero-config default relay:** desktop app connects to `ws://localhost:3000` out of the box; override via `BUZZ_RELAY_URL` env var or in-app relay switch.
- **One-command dev bootstrap:** `just setup && just build`, then `just dev` starts relay + desktop together. `just setup` auto-copies `.env.example` → `.env`, downloads pinned toolchains via Hermit, starts Docker (Postgres, Redis, MinIO, Adminer, Keycloak, Prometheus), and runs migrations — a single command stands up the full stack including OAuth/OIDC test infra.
- **Toolchain pinning is a hard default**, not a suggestion: Hermit pins Rust 1.88+, Node 24+, pnpm 10+, `just`, `lefthook` 2.1.3; CONTRIBUTING.md gives the literal apt-get line CI uses for Tauri/GTK system deps so local results match CI exactly.
- **Windows is a second-class-but-supported default**: agent shell tool assumes bash; Windows users must install Git for Windows for Git Bash, or set `BUZZ_SHELL` to a custom path — an explicit, documented default rather than a silent failure.
- **`buzz-cli` is agent-first by design default**: "JSON in, JSON out, designed for LLM tool calls" (README line 168); requires `BUZZ_PRIVATE_KEY`. `buzz doctor` (PR #4063) is designed to work even with a broken/missing key so the tool that debugs the environment isn't itself gated by the environment being debugged — dispatches before the credential gate.
- **One relay = one community by default**; multi-tenant hosting is opt-in and explicitly kept semantically identical to single-tenant at the client boundary (README "What is this, really?" section, and `buzz-db`/`buzz-search`/etc. crate docs on tenant scoping).
- **Frozen opinions visible in the "Works today / Being wired up / pending" table** (README lines 100–109): relay+channels+threads+DMs+canvases+media+search+audit log, desktop app, `buzz-cli`+ACP harness (Goose, Codex, Claude Code), YAML workflows, git events (NIP-34), git hosting all ship as defaults today. Push notifications, web-of-trust reputation, and "culture features" are explicitly marked as *not yet real* — a public commitment not to overclaim.

## 4. The adoption story

- **Tagline (README, top of file):** *"A workspace where humans and agents build together, on a relay you own."* Positioning line: *"Yes, it's another AI-adjacent developer tool. We're sorry. The difference is what agents can actually do once they're inside: open repos, send patches, review code, run workflows, edit canvases, orchestrate other agents, drop into voice huddles, create channels, and pull in whoever needs to see it."*
- **The pitch is substrate consolidation, stated explicitly:** *"The bet is that one community can do what teams currently fake with chat, forges, bots, CI dashboards, release tools, search indexes, and a pile of glue code. Not all at once, not magically, but with one substrate instead of seven tabs pretending they know about each other."* (README "Why Buzz is better")
- **Three named product narratives** used as the core sales pitch (README "Three little stories"): *Incident memory* ("have we seen this error before?" — agent searches six months of channel history and posts threads with root causes), *Branch as room* (a feature branch becomes a channel; patches, CI, review, and merge decision co-locate), *A release that writes itself* (workflow-triggered agent drafts release notes from merged PRs, posts for human 👍, then ships).
- **What users actually ask for / complain about (real issue titles as of 2026-07-31/08-01, `gh issue list`)** — these read as adoption/usage signal, not marketing copy:
  - #3996 "We need an 'Agent View' for remote agents" — user wants first-class UI for always-on headless bridge agents (Hermes/OpenClaw), because today they only show up as channel-member badges.
  - #4038 "Managed agent nest and memory store are shared across all communities: private workspace files and agent memory pool between tenants" — a user relying on Buzz's multi-tenant isolation promise finding a leak.
  - #4032 "security: `--private-key` as a CLI argument leaks the key into shell history" — active security-literate usage.
  - #3107 "Feature Request: Add ACP support for Oh-My-Pi... to leverage its high-performance Rust core and Anthropic Max subscriptions" — a user requesting integration with their own agent stack, evidence people are trying to plug their existing tools in rather than switch wholesale.
  - #4060 "A-RLS-1..5 conformance gate is specified in multi-tenant-relay.md but not implemented" and #3959 (maintainer-filed NIP-RS conformance gap) — users/maintainers holding the project to its own written specs, i.e., people who read the docs closely enough to file spec-vs-implementation mismatches.
- **19,722 GitHub stars, 2,005 forks** as of research date (`gh repo view`) — high fork-to-star ratio (~10%) is unusually high and consistent with people standing up their own relay/community rather than only star-and-forget.

## 5. UX and information architecture

- **Agent activity feed is a designed subsystem, not a log dump** — `VISION_ACTIVITY.md` specifies a full information architecture for showing agent work to humans:
  - Governing frame: every feed item renders as **verb, object, outcome** — *"Sent a message to #design." "Edited runtime.rs (+12/−3)." "Ran tests → 1248 passed."*
  - **Twelve render classes** in three tiers by read frequency: spine (Message, Buzz relay op, File-edit, Shell command, Tool status/turn lifecycle — "if these are unclear, the feed has failed"); high-value context (Thought, Plan/Todo, Permission, Error); ambient safety net (Generic tool fallback, Raw rail, Suppressed noise).
  - Explicit design rules: "Never go dark" (idle/waiting/timeout are rendered states, never silence — "if you didn't show it, it didn't happen"); "Failures rise, reads recede" (salience tracks consequence); "Resolve references" (show `#design` or a filename, never a raw pubkey/event id); "Coalesce streams" (chunked text becomes one message, not a packet trace); "Polished by default, raw on demand" (a raw rail exists as a zoom level on the same truth, not a separate feed).
  - Explicit non-Buzz-agent support: *"any compliant agent's messages, thoughts, tool calls, and turns become first-class items regardless of which tools it runs"* — protocol-honest rendering is the floor, Buzz-specific enrichment (diff rendering, semantic relay cards) is a layer on top.
- **Attention/catch-up surface: yes, and unusually deep.** Per §2 above, NIP-RS is a real unread/catch-up model with cross-device sync, hierarchical channel→thread→message frontier propagation (`effective(ctx) = max(merged[ctx], effective(parent(ctx)))`), and a manual mark-unread override CRDT layered on top. This is directly the "returning participant reorients" surface: the desktop client has dedicated components (`useUnreadChannels.ts`, `UnreadPill.tsx`, `UnreadDivider.tsx`, `useChannelUnreadState.ts`, `threadReplyUnreadCounts.ts`) plus mobile Flutter equivalents (`mobile/lib/features/channels/unread_badge/`), all keyed to this spec.
- **Provenance / trust display: human-vs-agent distinction exists at the identity layer, not a separate "verified vs claimed" badge system.** Every actor (human or agent) is a Nostr keypair; agents publish a `kind:10100` profile event that member lists and @mention autocomplete use to badge them as "agent" (issue #3996). No evidence was found in this pass of a UI element that distinguishes cryptographically-verified content from merely-claimed content beyond the underlying fact that *every* event in the system is Schnorr-signed by construction (NIP-01/NIP-42) — i.e., the trust model is "everything is signed, so there is no unverified tier to show," rather than a UI that visibly contrasts verified vs. unverified. Signature verification code lives in `crates/buzz-relay/src/handlers/{auth,event,ingest}.rs` and `conformance/mod.rs`, but this is server-side enforcement, not a client-rendered trust affordance.
- Screenshots referenced in README (`docs/assets/screenshots/channel-thread.png`, `channel-agents.png`, `create-channel.png`, `media-comments.png`) show: agents-in-channel-member-lists with emoji reactions, a channel-creation dialog with search/filters, and frame-anchored comments on video media — not independently verified beyond the README's own captions in this pass.

## 6. Velocity and process

- **Release cadence is roughly daily** for Buzz Desktop: `gh release list` shows v0.4.12 (2026-07-17) through v0.5.3 (2026-07-31) — 14 versioned releases in 14 days, i.e., about one release per day sustained over two weeks; v0.5.0 → v0.5.3 landed in 3 days (2026-07-28 to 2026-07-31).
- **CI gate (`.github/workflows/ci.yml`)**: path-filtered jobs (rust/desktop/desktop-rust/web/mobile) via `dorny/paths-filter`, each gated on `needs.changes.outputs.*`; jobs include `rust-lint` (fmt-check + clippy -D warnings), `unit-tests` (cargo-nextest), `desktop-core`, and — notably — a `changes` job that runs shell-script tests *of the release/CI machinery itself* (`scripts/test-release-ref-contract.sh`, `scripts/test-desktop-release-candidate.sh`, `scripts/test-mobile-release-contract.sh`, `scripts/test-mobile-worktree-overrides.sh`, plus `node --test scripts/check-file-sizes-core.test.mjs` — a file-size ratchet with its own unit tests). Nine total workflow files cover CI, two release pipelines, three canary builds (Linux/macOS/Windows), Docker, Helm charts, and a benchmark harness.
- **PR review norms are written down explicitly in CONTRIBUTING.md**: DCO sign-off is enforced by a CI "DCO Check" that blocks merge; squash-merge only, so PR titles become the `main` commit subject and must follow Conventional Commits; a documented list of "PRs we're unlikely to merge" (large refactors without prior issue discussion, cosmetic-only churn, unsolicited big features, drive-by unrelated changes bundled together); UI-changing PRs must include before/after screenshots because "we can't run every branch locally"; force-push during review is discouraged ("push new commits... it makes it hard to see what changed"); AI-assisted PRs are explicitly welcomed with no disclosure requirement but the contributor must "own and have reviewed the final code" — unreviewed AI submissions may be closed with a pointer to this policy.
- **Real PR discipline observed in the wild:** PR #4063 (`buzz doctor`) documents its own out-of-scope boundary in the PR body ("Out of scope (per the issue's own staging): WebSocket readiness probe... Deeper runtime diagnostics... Integration test against a real relay"), reports concrete test counts ("8 new unit tests... Full cargo test -p buzz-cli --lib: 279 passed, 0 failed... cargo clippy... clean"), and includes a self-filed follow-up commit fixing its own exit-code classification bug same-day, with an explicit before/after rationale in a PR comment.
- **Breaking protocol changes are handled by never breaking the wire format**, per CONTRIBUTING.md's Architecture Overview: *"Event kinds are the only switch... Adding a new feature means defining a new kind. No breaking changes to existing clients."* Kind-number sub-ranges are centrally registered in `buzz-core/src/kind.rs` with collision checking via an `ALL_KINDS` array — new capability is additive by construction, not by discipline alone.
- **No unsafe, no unwrap/expect in prod code, clippy `-D warnings` as a hard gate** — enforced project-wide (`#![deny(unsafe_code)]` per crate; CONTRIBUTING.md explicitly bans `unwrap()`/`expect()` outside tests).

## 7. The one thing

The single most impressive engineering decision in this repo is **NIP-RS's Full-State Load procedure** (`docs/nips/NIP-RS.md`, ~lines 299–379): a protocol-level proof that a client can establish *completeness* of its own read-state data against an adversarial-by-default relay (one that silently caps query results with no way to signal truncation), using only the standard Nostr filter surface — no new relay behavior required, just a descending-cursor enumeration with a derived cap-lower-bound (`C`), a proven floor (`L=2`), and a live-subscription "fence" established *before* enumeration begins and held for its duration to catch coordinates that move during the load. The spec explicitly states termination is "potentially incomplete" rather than silently wrong when completeness can't be proven, and backs the whole register algebra (tombstone floors, clear-wins tie policy, atomic per-context grouping) with an actual mutation-tested formal model (`docs/formal/nip-rs-unread/`, 9 mutants, each with a documented witness). Building a chat client is common; proving — with a bounded exhaustive model and a 9-mutant harness — that your "have I read this" state can't silently resurrect a cleared unread badge across devices, on a relay you don't fully trust to answer honestly, is not. This is directly on-point for a product whose central bet is "a returning participant can reorient faster": Buzz treats the reorientation primitive itself as a correctness-critical distributed system, not a UI nicety.
