# block/buzz — Failure Diary

Read-only mining of github.com/block/buzz (issues, PRs, git log at `origin/main` HEAD ≈ `bb34bc4`, ~2046 commits). Facts and quotes only.

## 1. Isolation and trust failures

**#4038** (open, filed 2026-08-01, author d3layd) — "Managed agent nest and memory store are shared across all communities." Every managed Claude agent on a Buzz Desktop install uses one on-disk nest (`~/.buzz`) and therefore one Claude-Code project-memory store, regardless of which tenant ("community") the agent belongs to. Reporter's own evidence: with 3 communities on one account, `RESEARCH/` was "8 of 9 files community-B," `OUTBOX/` "~30 files, nearly all community-B," `memory/` "5 of 10 memories community-B, indexed in the MEMORY.md that is auto-injected into every session." Quote: "Relay membership separates what agents can *say*; it does not separate what they *know*." **Defect class: shared mutable filesystem/memory store keyed by machine, not by tenant — a directory-scoped resource treated as if it inherited the relay's per-request tenant scoping.**

**#4060** (open, filed 2026-08-01, author Brad9474) — `docs/multi-tenant-relay.md` specifies an "A-RLS-1..5" conformance gate (Postgres RLS enabled + restrictive policy on every tenant table; non-bypass role; `SET LOCAL app.community_id` per transaction; `SECURITY DEFINER` audit; composite FK/unique constraints) as a *startup/CI assertion suite that rejects the deployment on failure*. Reporter searched `migrations/`, `crates/`, `deploy/`, CI workflows at the commit current at filing time: "zero hits outside `docs/multi-tenant-relay.md` itself." Table of axiom status: A-RLS-1/2/3 "Not met," A-RLS-5 "Appears met." Quote from the doc itself, cited in the issue: "A dropped application predicate yields ∅ under A-RLS ... proving RLS load-bearing, not decorative" — i.e., the docs claim RLS is the second of two defense layers, but only the first (application-level `router.rs` fencing) is real; the second is asserted, not implemented. **Defect class: a documented defense-in-depth layer with a named conformance gate ("a failing assertion rejects the deployment") that was never wired into CI or startup — the doc reads as a passing gate that doesn't exist.**

**Sibling isolation bugs found via search** (`tenant OR isolation OR leak OR cross-community OR sandbox escape`):
- **#3106** — "Per-account local workspace file leaks agent roster & relay info across communities." The shared `AGENTS.md` workspace file lists the *full* agent roster from every community under one account, with duplicated/undeduplicated entries; actual relay-side channel membership is correctly scoped, but the client-local artifact is not. 1 comment, still open.
- **#2515** — "Agents from different communities collide in channels, causing duplicate @mention targets and missing avatars." One friendly-name `@mention` can mint Nostr `p` tags for two same-named agent identities from *different* communities; the foreign identity can reply into the wrong community's channel, and its avatar breaks because the image URL points at the other community's media host.
- **#3371** — "Managed Claude agents inherit the owner's personal Claude Code config (global CLAUDE.md, auto-memory, hooks) — no isolation." Root cause is explicitly "two doors, both open": (1) the ACP adapter hardcodes `settingSources: ["user","project","local"]`, pulling the human owner's `~/.claude` config into every managed-agent session; (2) the agent nest lives inside `$HOME`, so Claude's *ancestor* project-memory walk finds `$HOME/.claude/CLAUDE.md` even after the `user` source is dropped — "merely dropping `user` is not sufficient." Verified reproduction with `claude --setting-sources project,local` still leaking the ancestor file. This is the same structural root (nest inside `$HOME`) that #4038 hits from the cross-tenant angle.
- **#3822** — RFC explicitly proposing `cwd` as a first-class per-channel input specifically to fix the shared-nest problem at its root: "Missing, ambiguous, or deleted workspace mappings fail clearly instead of silently falling back to the Buzz nest."
- **#3020 / e2e007910 (fixed)** — "Banned relay admins can still run NIP-43 admin commands (kinds 9030–9033) over HTTP." The durable-ban check was enforced only at the NIP-42 *WebSocket* auth handshake; the HTTP write path never consulted ban state, so a banned admin/owner could add members, remove members, change roles, and set the workspace icon via signed HTTP requests — "No open WebSocket required." Reported externally by a named security researcher; the fix PR notes it is "the same class as BUZZ-SEC-007, which PR #1915 closed for moderation command kinds 9040–9044. That fix was never extended to the 9030 range" — i.e., the same defect class recurred in a sibling code path after being fixed once elsewhere. **Defect class: an authorization check enforced at one transport/entry-point (WS auth) but not at a second entry-point (HTTP) reaching the same privileged operation.**
- **#3643** — "NIP-50 search pool uses READ_DATABASE_URL raw, bypassing all replica fencing — live in bb-block and bb-public today." A search code path reads directly off a replica connection string, sidestepping the freshness/fencing guarantees the rest of the read path enforces.
- **#3644** — "Writer-pointing READ_DATABASE_URL accepted silently; route telemetry reports replica/fresh from the writer." Misconfiguration (pointing the "read replica" URL at the writer) is accepted without validation, and the telemetry that's supposed to reveal staleness instead lies and reports "fresh."
- **c81b89355** (fixed, git log, no issue number found) — "fix(workflow): scope workflow execution and approvals to their community." `workflows`, `workflow_runs`, and `workflow_approvals` are keyed `(community_id, id|token)` but the execution/approval spine "fetched, listed, mutated, and posted by bare id," so "a webhook/manual trigger or NIP-09 deletion in community B could load, drive, or erase community A's colliding workflow" when UUIDs collided across tenants, and "workflow side effects were published under the deployment/default tenant instead of the run's own community." Commit message explicitly calls out `bind_deployment_community(relay_url)` as "the Issue-4 root cause." **Defect class: composite tenant key exists in the schema but application-layer lookups used the non-tenant half of the key, so cross-tenant collisions on the free half (UUID/token) leaked reads/writes.**
- **3dc8606bc** (fixed) — "fix(relay): restore community write fence on persistent ingest." A prior "checkpoint" commit had *removed* a pre-lease fence assert from the ingest path "without a replacement," leaving the persistent-event write seam unfenced during community deletion — i.e., an isolation guard regressed away and had to be restored as a fail-closed `is_serving_active` check. **Defect class: a security-relevant guard was silently dropped during an unrelated refactor and only caught later.**

## 2. The fail-open class — specified-but-not-implemented, silent, no-op

- **#4060** (above) — the flagship case: a whole conformance gate ("A-RLS-1..5") described in docs as fail-closed ("a failing assertion rejects the deployment") but never implemented; reference `docker-compose.yml` "discharges none of it."
- **#3525** — "WF-08: approval gate is ~90% built — finalize_run drops the token instead of creating WaitingApproval." The suspend/resume/approve/deny machinery is fully implemented end to end, but `finalize_run` still hits a stale guard: `if result.approval_token.is_some() { // Approval gates are not yet implemented (WF-08). ... RunStatus::Failed, ... "approval gates not yet implemented — see WF-08" }`. The comment was accurate when written; nothing updated it once the feature landed, so a completed feature silently fails-closed to `Failed` instead of working. Docs (`VISION.md`, `ARCHITECTURE.md`) still describe it as unbuilt.
- **#4033** — "Partition manager cannot reclaim a pre-existing catch-all partition — monthly partitioning silently stops." A Postgres `42P17 ("would overlap partition")` error from the monthly-partition-create path is caught and logged at `info`, then treated as success: `// Fresh schemas include a right-edge catch-all partition (*_p_future). If it already covers this month, the table is still safe for writes; treat the overlap as "ensured" rather than failing startup.` Reporter: "partitioning for that range silently and permanently stops, with no error, no metric, and no operator-visible signal." Recurs for every fresh install going forward. **Defect class: an expected-error carve-out (added for one real edge case) silently swallows a *different*, unbounded failure mode that shares the same error code.**
- **#3468** — "same-second command events lose a coordinate tie-break and are discarded as `accepted:true`." NIP-33 coordinate-replacement dedup applies to *every* event carrying a `d` tag (gated on tag presence, not on the event kind being genuinely replaceable), and ties are broken on raw event-id ordering rather than causal order — so a `workflows update` issued in the same wall-clock second as a prior write is silently dropped, "reported as `accepted: true`, exit 0," while the executor keeps running stale YAML. Reproduced: "Twelve updates in a tight loop lost 3 of 12... Five manual triggers in one second produced 2 runs."
- **#2534** — `kind:0` profile republish "drops every field outside a 5-key allowlist — silently deletes `bot: true`, `nip05` and `website`."
- **#2459** / **#2698** — turn/session completes with `outcome=ok` inside the agent runtime, but the reply is silently lost: in #2459 because the agent's own `buzz` CLI write fails after a successful turn; in #2698 because "reply delivery is implicit" and Sonnet-class agents answer only in session text with no explicit publish call, so "every reply is silently dropped."
- **#2837** — `buzz-admin` "silently falls back to hardcoded dev database credentials when `DATABASE_URL` is unset" — a missing-config condition that should fail closed instead defaults to a known credential.
- **#3033** / **#2444** — agents "silently stop responding" because of a `localhost` vs `127.0.0.1` host mismatch between the harness dial target and the community's configured origin — same defect class appearing at least twice (desktop spawns agents on one host string, the relay/community is configured with the other).

## 3. Agent misbehavior in shared spaces

- **#4065** (open, filed 2026-08-01) — "Agent unresponsive: Buzz did not reply to @mention in thread." Filed by the agent itself as a self-report. Root cause per the issue: single-threaded turns with no streaming/intermediate updates — a ~6-minute turn (workflow creation + memory updates + a concurrent, unrelated investigation the agent decided to interleave) produced total silence while the owner sent an increasingly frustrated follow-up ("@Buzz why no answer????????") 7.5 minutes after the first message. Quote: "Concurrent @mentions don't interrupt — When a new mention arrives while a turn is running, [] mode merges it but doesn't surface that the agent is already busy." This is a first-person account of an agent absorbing an unrelated task mid-turn without signaling scope change to the human.
- **#3749** (closed) — "Agents read messages (👀) but never reply — persists through reboot." The agent visibly acknowledges (read receipt emoji) but never produces output, and the condition survives a restart.
- **#2062** — "Relay-mesh agents silently stop replying if mesh runtime drops after launch (no self-heal)." No periodic liveness re-check ties the local model-serving runtime to agent dispatch; once the runtime dies, "bots go quiet with no indication why. This is the dominant 'shared compute is broken' user-facing symptom even though discovery, transport, and remote serving are all healthy." Only a manual agent restart re-arms it.
- **#3831** — "Agent stays 'online' after its Claude credentials expire — every mention fails with -32000, nothing surfaces it." Headless/Docker-deployed agents kept presence "online" for a day+ after auth expired; every subsequent turn errored, invisibly. Reporter's ranked wishlist: presence should change after N consecutive error turns; the harness should post the failure into the channel where the human is already looking; a non-zero exit should let the process supervisor notice. Quote: "Presence seems to reflect the harness's websocket, not whether the agent can actually do anything."
- **#3969** (open) — after a relay rate-limit NOTICE burst on reconnect, `buzz-acp` "goes permanently silent forever — literally zero further log lines of any kind... while remaining 'online' in the UI." Reporter did source-level analysis of the gate logic and unit tests before concluding they couldn't isolate the hang point — an example of a bug surviving specifically *because* the obvious suspect (the rate-limit gate) was already well-tested and defended, and the real hang is elsewhere downstream.
- **Reply-delivery revert cluster** (git log, 2026-07-30, all four commits within ~24 minutes, same author): `463b47d67 revert(agent): drop reply delivery MCP hook`, `b8a0f468f Revert "feat(acp): propagate automatic reply context"`, `a86598a3c Revert "fix(cli): allow explicit top-level messages"`, `0136bef89 Revert "fix(mesh): bound local agent generation"`. Four related agent-reply/reply-delivery changes landed and were reverted in the same short window — evidence that reply-delivery mechanics were being actively fought over/destabilized around that date rather than converging.
- **runaway cost/compute**: search for "runaway/infinite loop/cost spike/token spend" returned zero issues — no evidence found either way in the tracker (absence, not a confirmed non-issue).

## 4. Sync/consistency bugs

- **#4049** (open) — "Share compute stuck at 'Starting…' — layer download hangs at ~70 MB." A downstream diagnostic comment traced it into a vendored/pinned SDK crate (`mesh_llm_host_runtime`) whose chunk/resume reader wedges at a fixed byte offset across restarts, "including fresh installs" — the byte-progress sink goes permanently short with no retry or surfaced error. The comment separates this from a second, independent bug (a UI validator rejecting the `file://` scheme the same UI advertises) and recommends splitting the fixes because the primary defect lives in a vendored dependency, not first-party code.
- **#3383** — "Desktop catch-up escalates @channel markers from before the reader joined (badge-without-row)" — catch-up/backfill surfaces notification badges for events the reader was never a member for, with no underlying row to show.
- **#3215** — "Desktop reconnect replay re-alerts old thread replies and plays false notification sound" — reconnect replay is not de-duplicated against what was already seen, so old events re-fire notifications.
- **#3265** — "after a relay reconnect the channel view can go permanently blank — resubscribe reuses the subscription ID, relay silently drops it, UI shows an empty channel with no error." Subscription-ID reuse on resubscribe collides relay-side and is dropped without any client-visible signal.
- **#3975** — "Desktop client fails to re-establish dropped relay socket; 'Reconnect' ineffective, only full relaunch recovers."
- **#2471** — "Desktop blind-retries an oversized (~66KB) frame on join — reconnect storm against relays with the 64KB limit." A retry loop with no backoff/size-check hammers a relay with a frame it can never accept.
- **#3156** — "Channels with more than 1000 members silently truncate the relay roster (kind 39002): wrong counts, dropped mentions, broken admin actions." An unbounded-membership assumption baked into a fixed-size roster event.
- **#3848** — "NIP-IA archive snapshot can lose rapid same-second updates" — same second-resolution timestamp/tie-break class as #3468, in a different subsystem (archive snapshotting vs. command-event dedup) — recurring root cause (second-resolution `created_at` used as a uniqueness/ordering key) surfacing independently in at least two subsystems.

**Fixed fast** (closed issues sorted by created→closed latency; smallest observed real-bug latencies, excluding same-day mislabels/withdrawals):

**Lingers** (old open issues, oldest-first among non-meta/non-proposal bugs):

Notable because the issue text itself calls it "the dominant 'shared compute is broken' user-facing symptom," yet it has sat open for weeks — a case where an issue can be simultaneously high-impact by the reporter's own account and low-velocity in practice, likely because shared/local compute is a less-traveled path than hosted relay + cloud model usage.

## 7. Security posture

`SECURITY.md`: private disclosure only via `buzz@block.xyz`, 48h acknowledgment / 7-day full-response target, coordinated disclosure, reporters credited unless anonymous. Documented security model: NIP-42 (WS) / NIP-98 (HTTP) signature auth; **channel membership is the only authorization mechanism** — no separate ACL/capability system ("If a principal ... is a member of a channel, they can read and write to it. If they are not a member, the relay rejects their requests — even if they are authenticated."); append-only SHA-256 hash-chained audit log, explicitly "tamper-evident but not tamper-resistant: ... an attacker with database write access can recompute the entire chain after editing"; OS-keyring secret storage with verified round-trip migration and a documented fail-safe (keyring unreachable ⇒ keep reading plaintext, don't migrate, so a transient outage "cannot resurrect a rotated key from a leftover file"); SSRF-blocklist on workflow webhooks; sandboxed/timeout-bounded `evalexpr`; `cargo audit` in CI; `#![deny(unsafe_code)]` repo-wide. No published GitHub security advisories found (`gh api repos/block/buzz/security-advisories` → empty) despite at least one externally-reported, named-reporter vulnerability fixed in-repo (`e2e007910`, the NIP-43 banned-admin bypass, credited to "Bilal Syed" in the commit body, also independently filed publicly as #3020 before the reporter read SECURITY.md) — i.e., the private-disclosure channel is used and fixes land, but no advisory has yet been published to match the policy's own stated disclosure step. That same fix PR explicitly scopes out two adjacent known gaps rather than closing the whole class ("This does not close the class. Two separate items remain open, deliberately excluded to keep an externally-known security fix reviewable"), including that command-kind dispatch (`is_command_kind`) fires ~80 lines *before* the restriction gate with "no restriction read" in `command_executor.rs` — measured live: "a banned member can still open a DM (41010 → 200)."

## Summary of transferable defect classes for Atrium

1. Shared mutable filesystem/memory keyed by machine/process, not tenant (#4038, #3371) — any durable per-agent state store needs the tenant/community id in its storage key from day one, not bolted on after the relay-level scoping ships.
2. A documented "fails closed" gate that was never wired into CI/startup (#4060) — conformance claims in docs must be backed by an actual assertion that runs, or the doc is worse than no doc.
3. Composite tenant keys in schema but bare-id lookups in application code (c81b89355) — the recurring root cause across several isolation bugs; every lookup/mutation/side-effect path touching a tenant-scoped table needs an explicit audit, not just the schema constraint.
4. Same authorization check enforced on one transport (WS) but not a second (HTTP) reaching the same operation (#3020/e2e007910) — and the same *class* of gap recurring in a sibling code path after being fixed once (9040-9044 fixed, 9030-9033 missed).
5. Stale "not yet implemented" guard comments outliving the feature they guard (#3525) — a fail-closed placeholder becomes a silent regression once the real implementation lands underneath it without removing the guard.
6. Expected-error carve-outs that also silently swallow an unrelated, unbounded failure mode sharing the same error code (#4033).
7. Second-resolution timestamps used as uniqueness/ordering keys, causing silent same-second write loss — recurring independently in at least two subsystems (#3468 command events, #3848 archive snapshots).
8. Turn-based/single-threaded agent execution with no intermediate status signal, so a long or scope-creeping turn reads as total silence to the human waiting on it (#4065, live self-report from the agent under study).
9. Presence/liveness reflecting transport connectivity rather than actual task-completion capability, so a broken agent shows "online" indefinitely (#3831, #2062, #3969).
