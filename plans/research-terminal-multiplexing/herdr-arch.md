## 1. What herdr is
herdr is a native, single-binary Rust terminal workspace manager built specifically to babysit multiple AI coding-agent CLI processes (Claude Code, Codex, Cursor Agent, Devin, OpenCode, etc.) at once. It runs a persistent background **server** process that owns real PTY-backed terminal processes ("panes") organized into workspaces/tabs/panes, plus one or more **client** processes (the actual TUI, built on `ratatui`) that attach/detach from that server, tmux-style. It detects each pane's agent and its semantic state (`blocked`/`working`/`done`/`idle`/`unknown`) from screen content and integration hooks, rolls that up into a sidebar, and exposes a local socket control API so scripts and the agents themselves can drive panes. Cargo.toml description: "terminal workspace manager for AI coding agents." There is **no browser or web client** anywhere in the codebase — it is a terminal (TUI) application only, not a web UI. `src/client`, `src/ui`, and `src/pane` all render into the user's existing terminal via `ratatui`; the "remote" feature is SSH-based remote attach (a local herdr binary bridging over SSH to a remote herdr server), not HTTP/browser remoting.

## 2. Does it do terminal multiplexing, and how — the full stack
Yes, natively, but the stack is a native-TUI stack, not a web stack:
- **PTY layer**: `portable-pty` (the wezterm crate), pinned to `=0.9.0` and **vendored + patched** at `vendor/portable-pty` (`Cargo.toml`: `[patch.crates-io] portable-pty = { path = "vendor/portable-pty" }`). Two carried patches (`vendor/patches/portable-pty/0001-control-conpty-loading.patch`, `.../0002-windows-raw-command-tail.patch`) fix Windows ConPTY DLL-loading security (issues #761, #1533) and cmd.exe argv-quoting for custom commands (#1041). PTY spawn/IO lives in `src/pty/actor.rs` (+ `src/pty/actor/unix.rs`, presumably `windows.rs`) and `src/pty/backend.rs`/`fd.rs`: an actor per pane with a bounded `mpsc` channel for input writes (`try_write_user_input` / `write_user_input`, backpressured — test `actor_reads_output_while_input_is_backpressured` in `src/pty/actor/unix.rs`) and a separate control channel for `Resize`/`Shutdown` commands.
- **Terminal/VT engine**: not xterm.js, not a from-scratch grid — herdr vendors **libghostty-vt**, the VT/grid engine extracted from Mitchell Hashimoto's Ghostty terminal (Zig, MIT license, `vendor/libghostty-vt/LICENSE`), and calls into it over FFI (`src/ghostty/bindings.rs` — 352KB of generated bindings — and `src/ghostty/mod.rs` — 133KB of safe wrappers). This engine owns the terminal grid, cursor, scrollback ring, hyperlink/OSC-8 state, and cell attributes; herdr carries one patch on top (`vendor/patches/libghostty-vt/0001-default-grapheme-cluster-mode.patch`).
- **Transport**: `src/protocol/wire.rs` defines a **custom binary protocol over Unix domain sockets** (named pipes on Windows), length-prefixed (u32 LE), versioned (`PROTOCOL_VERSION = 19`), capped at `MAX_FRAME_SIZE = 2 MiB` (32 MiB for Kitty-graphics frames, 16 MiB for clipboard-image bridging). This is the server↔TUI-client rendering/input channel. Separately, there's a documented **socket control API** (`src/server/client_transport.rs`, `client_accept.rs`) that speaks newline-delimited JSON over the same kind of local socket, for scripts/agents (`herdr pane read`, `agent.wait`, `events.subscribe`, etc.) — not for interactive rendering.
- **Renderer**: two negotiated modes (`RenderEncoding` enum in `wire.rs`): `SemanticFrame` (structured `FrameData`/cell diffs, compared frame-to-frame and skipped when unchanged — see `src/server/render_stream.rs::ClientRenderState::Semantic`) for the native ratatui client, and `TerminalAnsi` (already-diffed ANSI byte streams via a `BlitEncoder`) for lower-level bridges. Local rendering itself is `ratatui` (a Rust TUI widget/grid library), not xterm.js and not a canvas/WebGL grid.
- **Session persistence and reattach**: see section 3.
- **Resize/SIGWINCH**: pane resize is a message through the same actor control channel (`PtyIoActorHandle::resize(rows, cols, cell_width_px, cell_height_px, ...)` in `src/pty/actor.rs`), which calls `portable-pty`'s `master.resize()` (this issues the underlying `TIOCSWINSZ`/`SIGWINCH` to the child). Cell pixel dimensions are carried alongside rows/cols specifically to keep Kitty/Sixel graphics proportional across resizes. Resize is not friction-free in practice — see section 6.
- **Scrollback**: owned entirely by the vendored ghostty VT engine, not by herdr's Rust code. `Ghostty::new(cols, rows, max_scrollback)` takes a byte-size scrollback cap (`src/ghostty/mod.rs:742`); tests confirm `max_scrollback = 0` disables history entirely and a larger byte cap retains proportionally more rows. Herdr's own `[experimental] pane_history` setting (see below) is a distinct, opt-in feature for persisting recent screen contents to disk across a full server restart — separate from live in-memory scrollback.
- **Arrangement**: a workspace → tab → pane tree (BSP-style binary splits — `layout.export`/`layout.apply` describe the tab layout as a tree of `split`/`pane` nodes with `direction: right|down` and a `ratio`), not a full tmux-style arbitrary tree and not a "tile all streams" grid mode. Panes can be split right/down, swapped, zoomed, and moved across tabs/workspaces; there's also a "popup" placement (session-modal, floating, outside the tiled layout) used by plugin panes — closer to a picture-in-picture concept but plugin-only, not a general terminal PiP.

## 3. The multiplexing model specifically
It is a **custom session manager**, not tmux/screen under the hood (no shelling out to `tmux`/`screen`; the PTY, VT state, and layout tree are all herdr's own Rust/FFI code, tmux-*style* only in its keybinding UX — `ctrl+b` prefix, `q` to detach). Per docs (`website/src/content/docs/session-state.mdx`, `concepts.mdx`):
- **Browser refresh**: not applicable — there is no browser client.
- **Client disconnect**: fully survives. Server owns panes/processes; detaching (`ctrl+b q`) leaves the server and all child processes running. This is called out as "the strongest persistence path because the original processes never stop."
- **Server restart**: processes do **not** survive (the actual child PTYs die with the server). What comes back is a **snapshot restore** — workspaces/tabs/panes/cwd/layout/focus reconstructed from a saved `session.json`, with panes relaunched as fresh shells in their saved directories. Optional **pane screen history replay** (off by default, opt-in via `[experimental] pane_history = true`, persisted to `session-history.json`) restores what the screen *looked like*, not the process. Optional **native agent session restore** (on by default) re-invokes specific agent CLIs' own `--resume`/`--session` flags (a table of ~14 supported agents and required "Herdr integration" versions is in the docs) so the *agent's own* conversation state resumes even though the underlying process is new.
- **Live handoff** (`herdr update --handoff`, experimental/opt-in): the old server transfers live pane PTYs/processes to a replacement server process during an update, so processes genuinely survive a server binary swap — but in-flight API requests/waits/subscriptions are dropped and must be retried by the client.
- **Buffer ownership**: the server process owns the buffer (grid + scrollback) at all times, via the vendored ghostty VT engine instance per pane; the socket API's `pane.read` and the observer/controller bridge stream from that server-owned state, they don't hold their own copy of truth.

## 4. Security and isolation
There is no multi-tenant/browser trust boundary to speak of — herdr's whole model assumes a single local user (or one SSH-authenticated remote user) owns the server:
- **Socket permissions**: the control socket is chmod'd `0o600` (owner read/write only) — `SOCKET_PERMISSION_MODE` in `src/server/socket_paths.rs`. That's the entire authorization model for the local/control API: OS file permissions on a Unix domain socket (named pipe ACLs on Windows), not a token/cookie/auth-header scheme.
- **Remote/SSH**: `herdr --remote host` is a thin local client that SSHes to the target and starts/attaches a herdr server there, using the user's normal OpenSSH authentication (keys, agent, passphrase prompts) — no herdr-specific auth layer. Docs explicitly note it manages its own temporary SSH config/control-socket for connection reuse unless `[remote].manage_ssh_config = false`.
- **Workspace/user scoping**: none in the multi-tenant sense — "workspaces" are just project containers for one local user, and "named sessions" are separate local server instances/sockets, not access-control boundaries.
- **Frame-size caps** (`MAX_FRAME_SIZE = 2 MiB`, `MAX_GRAPHICS_FRAME_SIZE = 32 MiB`, `MAX_CLIPBOARD_IMAGE_PAYLOAD = 16 MiB` in `src/protocol/wire.rs`) are described in-source as anti-DoS ("Frames larger than this are rejected to prevent denial-of-service via oversized length prefixes") but scoped to the local wire protocol, not to a network-facing service.
- **Explicitly out of scope / not addressed in docs**: no browser sandboxing story, no per-user/per-workspace authz, no mention of a hosted/multi-tenant deployment mode, no CSP/XSS considerations (none of that surface exists). Windows ConPTY loading was hardened specifically against DLL-search-path hijacking (patch 0001) — that is the one place "security" is discussed concretely in the source, and it's about the local binary's own DLL loading, not about remote/browser exposure.

## 5. Performance choices
- **Anti-flood strategy is coalescing + diffing, not rate-limiting per se.** The main headless server loop (`src/server/headless.rs`) is signal/dirty-flag driven: PTY reader threads set a shared `render_dirty` flag; the loop drains that flag once per iteration ("1. Check the coalesced render signal from PTY readers and generic runtime work") and renders once regardless of how many PTY read events fired in between. A `yes`-style flood therefore collapses to one re-render per loop iteration instead of one per line of output.
- **Diffing on top of coalescing**: `src/server/render_stream.rs`'s `ClientRenderState` keeps either a `last_frame` (Semantic clients skip re-sending identical frames) or a `BlitEncoder` (TerminalAnsi clients get an ANSI *diff*, not a full repaint) — so even a coalesced render only ships the changed cells over the wire.
- **Bounded channels for input, not output**: input writes to a PTY go through a bounded `mpsc` channel that can reject with backpressure (`try_write_user_input` returns `TrySendError`); there's an explicit unit test (`actor_reads_output_while_input_is_backpressured`) confirming reads still proceed while input is backpressured, i.e., a stuck writer can't starve the reader side.
- **Frame size ceilings** (2 MiB / 32 MiB for graphics / 16 MiB for clipboard images) act as hard caps on any single wire message.
- **Scrollback is byte-budgeted**, not row-budgeted or unbounded (`max_scrollback` passed to the ghostty engine in bytes; `0` disables history).

## 6. What they got right, and what is visibly hard
From `CHANGELOG.md`, `git log` over `src/pty`, `src/terminal`, `src/ghostty`, `src/pane/terminal.rs` (39 changelog lines mention pty/scrollback/resize/sigwinch terms), and open/closed issue search:
- **Continuously and heavily fixed**: per-agent quirks riding on top of the terminal layer — Windows-specific pane behavior (shift-enter, ConPTY DLL loading, cmd.exe quoting), individual coding-agent lifecycle/detection heuristics (Hermes, Kimi, others), copy-mode text-selection edge cases, clipboard paste corner cases, XTWINOPS/size-query answering inside panes, palette inheritance. Sample of the last 13 commits touching these paths: `fix: expand copy-mode word-end window past a final wide glyph (#2145)`, `fix(input): preserve native key lifecycle across routing (#2142)`, `fix: read alternate-screen agent history`, `perf: skip rendering hidden pty updates`, `fix: preserve shift-enter in windows panes (#1909)`, `fix: harden hermes lifecycle detection`, `fix: answer XTWINOPS size queries in panes`. This is a pattern of continuous, small, agent/platform-specific patches rather than architectural churn in the core VT/PTY pipeline itself.
- **Visibly hard / still open**: resize propagation and scroll-position stability across resize and detach/reattach (open issues #1709 "closing a split leaves the surviving pane stuck at the old narrow width", #1816 "a key event resizes the other panes; the same key as raw bytes does not"; closed-but-recent #2082 "Pi pane scroll position is lost on terminal resize", #985 "reattaching to another terminal leaks direct_attach_resize_locks"); Windows/WSL rendering fidelity (open #2146 "WSL: pane graphics render blurry — cell size is 8x16 while the terminal reports 10x21 via CSI 16t"); copy-mode/scrollback interaction with live output (open #680 "copy mode selection follows live output instead of freezing the view"); crash-window data integrity in the snapshot/history save path (closed-but-notable #1156 "Crash between session and history saves can restore wrong scrollback"). No explicit reverts of PTY/terminal work were found in the inspected (shallow, depth-100) commit window.
- **What they got right, by design choice rather than luck**: not writing their own VT parser (vendoring Ghostty's, a battle-tested implementation, instead) and not writing their own PTY layer (vendoring/patching `portable-pty` instead of reimplementing), so their own bug surface is concentrated in orchestration (actor lifecycle, resize propagation, session persistence, agent detection) rather than in ANSI/VT correctness itself.

## 7. Reusable as a library
Not really, as shipped:
- `libghostty-vt` (`vendor/libghostty-vt`) is itself a genuinely extractable, independently-licensed (MIT) VT engine from the Ghostty project — reusable on its own merits, but it is *not* herdr's own IP; herdr just vendors + FFI-wraps it (`src/ghostty/bindings.rs`, `mod.rs`) and carries one small patch.
- `portable-pty` is the well-known wezterm crate, also independently reusable, with herdr carrying two small Windows-specific patches on `0.9.0` (`vendor/patches/portable-pty/`).
- Herdr's *own* multiplexing logic (`src/pty/actor*`, `src/terminal/*`, `src/pane/*`, `src/protocol/wire.rs`, `src/server/*`) is not published as a separate crate, has no documented public Rust API, and is licensed Apache-2.0 as part of the whole `herdr` binary — technically usable as a library since it's Apache-2.0, but there is no crates.io publish, no `pub` API surface documented for external embedding, and the code is organized as a binary application, not a library crate (`Cargo.toml` has no `[lib]` section visible at the top level for this purpose).
- The one thing that **is** a documented, stable, externally-consumable interface for bridging herdr's terminals elsewhere is the **socket API** itself (`herdr terminal session observe|control`): newline-delimited JSON `terminal.frame` records with base64-encoded ANSI bytes out, and `terminal.input`/`terminal.resize`/`terminal.release` JSON commands in, over stdin/stdout of a spawned `herdr` subprocess. That is a real, documented, protocol-level (not library-level) integration point that something like a Next.js/WebSocket layer could shell out to and relay — it's a subprocess bridge, not an embeddable library.

## 8. Bottom line for the stated question
herdr is not a web UI and does not attempt to be one — it is a native TUI (ratatui) terminal application with a Unix-socket client/server split. It has no WebSocket/HTTP/SSE server, no xterm.js or canvas renderer, and no browser trust model; "remote" means SSH, not browser access. Its concrete engineering choices (vendor a real VT engine instead of writing one, vendor+patch a real PTY crate instead of writing one, coalesce+diff render output instead of streaming every byte, cap frame/scrollback sizes explicitly, keep resize as an explicit sized message rather than an implicit side effect) are the transferable ideas; its actual code is not something a Next.js/Postgres/WebSocket product would import or embed. The one literally reusable integration surface is the `herdr terminal session observe/control` subprocess bridge (JSON-framed ANSI frames over stdio), which is the shape a browser-facing bridge would need to reimplement itself with WebSocket/SSE, xterm.js (or similar) as the renderer, and node-pty as the PTY layer, since herdr supplies none of those three for a browser context.
